# v1.3 additive contract — remote model discovery and selection

All v1/v1.1/v1.2 methods remain compatible. The host reports `protocolVersion: "1.3"` and adds host capability names `modelList` (when `model.list` below is available) and `modelSelect` (when `session.setModel` below is available). Old clients accept the same major version and ignore unknown capability names. A client must never infer support from the version string alone: the two capability names are the only support signal. A host that lacks either method omits its capability name and the new methods return `-32004` with a bounded reason; it must not return a placeholder success. A new client against an old host (no `modelList`) degrades to "model selection unavailable — host does not advertise `modelList`" with that explanation; it must not guess a model list.

## Model (v1.3)

`Model`: `{id,provider,providerName,name,isDefault,selectable,reasoningEfforts?:[string]}`.

- `id` is the stable route id in the exact form `<provider>/<model>`. It is the only value a client may pass as `session.create.model` or `session.setModel.model`. At most 512 characters.
- `provider` is the host-side provider route id (provider identity, never a locator); at most 200 characters. `providerName` is its display name, at most 200 characters. `name` is the model display name, at most 200 characters.
- `isDefault` marks the host catalog default used for sessions with no explicit selection. At most one `Model` in a response has `isDefault: true`; `model.list.default` mirrors it (or describes a default outside the returned list).
- `selectable` reports whether the host currently permits selecting this model (for example a model of a provider that is not routable is enumerated but not selectable). Only `selectable` models may be supplied to `session.create.model` / `session.setModel`.
- `reasoningEfforts` lists the exact adapter-owned effort ids, matching the v1 `Provider.models[].reasoningEfforts` rule.

## Methods

| Method | Params | Result |
|---|---|---|
| `model.list` | `{}` | `{models:[Model], default:{provider,model,reasoningEffort?}|null, failures:[{provider,reason}], truncated:boolean}` |
| `session.setModel` | `{sessionId, model, reasoningEffort?}` | `{model:{provider,model,reasoningEffort?}}` (the normalized selection now installed on the Session) |

`model.list` is read-only and host-generation scoped: no session or workspace scoping, no provider network beyond the host's own catalog generation, and no side effects. `failures` lists providers whose catalog could not load (reason at most 500 characters). Reasons may summarize provider errors; they must never contain credentials, tokens, endpoints, or filesystem paths (v1 no-secrets rule).

## Bounds

`models` contains at most 256 entries (`truncated: true` when more exist); `failures` at most 16 entries. Fields exceeding their limits are omitted (model) or truncated (failure reason), never partially escaped. The complete response still fits the 28 MiB frame rule from 001.

## Errors

- `-32004` unavailable: `{data:{method:"model.list"|"session.setModel", reason:"catalog-unavailable"|"select-unavailable"}}` when the host runtime exposes no model catalog or no selection verb (capability absent).
- `-32004` with `data.nativeCode: "session/model-unavailable"` (001 mapping) when the host refuses a requested model or reasoning effort.
- `-32002` unknown Session or a Session outside the allowlist for `session.setModel`.
- `-32602` invalid params (missing/oversized strings).

## Selection paths

1. **Model chosen at Session create (primary).** `session.create.model` (and `reasoningEffort`) carries a `model.list` id. On a 1.3 host the requested model must be validated against the live catalog before the Session is created: an unknown, non-selectable, or model-catalog-failed request returns `-32004` `{data:{method:"session.create", reason:"model-unavailable"}}` and creates nothing. A 1.2 host keeps its pass-through behavior; clients therefore only send explicit models when `modelList` is advertised.
2. **Existing Session (offered).** `session.setModel` is offered when the host advertises `modelSelect`. Applying a selection to a running Session follows native semantics; failures are structured errors and never change what the next turn uses silently — the durable selection fold remains authoritative. A transport failure with an unknown outcome (connection lost before the response) is an uncertain outcome: the client never auto-retries `session.setModel`, and must re-read the Session's projected selection / `model.list` to decide what to show.

## Remote-model non-fallback (normative)

A remote Session acts only on models owned by its host. Clients must never substitute, merge, or display locally configured model entries for a remote Session, never send a local model id to these methods, and never silently drop a requested model: when `model.list` fails, is not advertised, or a chosen model cannot be validated, the operation fails with a structured error naming the method and the failing capability (`modelSelection` on the PC native seam; `modelList`/`modelSelect` on the wire). When `model.list` succeeds with an empty `models` array plus `failures`, a client may still create a Session without an explicit model — that yields the remote host default, which is a remote selection and is allowed; falling back to any local model is not.

PC native adapter (004 Revision B): the frozen seam keeps `ExternalSessionCapabilities.modelSelection = false` for external bindings, so the core's model seat — which reads the one Host-generation local catalog — stays hidden and local model names can never render against a remote Session. The remote catalog is surfaced through a plugin contribution on the official composer seam `conversation.input.right` (the list-kind "compact controls before the composer submit action", adjacent to the model seat): it renders the verified host's `model.list` for the selected external Session, renders nothing for non-external Sessions, and shows the explicit unavailable state when the host omits `modelList`/`modelSelect`. It cannot mount on the named `conversation.input.model` seat itself: that slot is `kind: 'single'` with one static winner, so a second registration there either throws (same priority) or shadows the core seat for every Session — which would strip the local catalog seat from local Sessions. Exactly one model control renders in every state. Model ids remain opaque strings end to end; a remote selection must never be dispatched to a local Session id or a local `selectModel` call — external ids stay namespaced and the local rejection path stays intact.
